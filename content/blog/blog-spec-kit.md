# 0到1的 AI規格驅動開發全端專案開發心得

@klif hsu

AI 寫程式最大的問題，不是它寫不出來，而是遇到沒講清楚的地方，它會自己補上，而且不告訴你。這篇整理我在讀書會分享的 spec-kit：它怎麼用「先寫規格」解決這件事，以及我實際用下來的心得。

## 一個十分鐘做好的登入頁

我最早用 vibe coding 幫家人做一個瓦斯訂單系統。第一步是登入頁：消費者和供應商都要能登入。

下完 prompt，大概十分鐘，AI 就做好了。我測了一下，註冊、登入都成功，也接上了後端資料庫。但問題來了：

1. **我沒說登入後要去哪一頁**，它就停在原地。
2. **密碼我有自己的規則，但我沒說**，它就自己訂了一套。

十分鐘生出來的程式，前後端加起來好幾百行，我沒辦法一行一行看，只能用測的。這兩個問題剛好測得到，那測不到的呢？後來我花了不少時間回頭翻程式，才找出 AI 到底自己決定了哪些事。

我想通了一件事：**不是 AI 做不到，是我沒把需求講清楚**。它不知道的地方，就自己補上，好把東西交出來。

那我為什麼沒講清楚？因為我根本沒有寫規格的習慣。

## 為什麼現在需要規格

沒有寫規格的習慣，不只是我。背後有兩個原因。

### 問題一：規格一直是配角

在傳統開發裡，需求與設計文件常常寫完就被擱置。我以前待的團隊，只有客戶要文件的時候，主管才會叫我寫。文件是寫給客戶交差用的，不是拿來開發的。

程式一直改，文件就要手動跟著改。這個成本太高，久了沒人改，大家只相信程式碼。spec-kit 的官方文件說得很貼切：規格就像鷹架，開始寫程式之後就被拆掉了。

### 問題二：AI 寫得比人讀得快

AI 產生程式碼的速度，遠超過人審查的速度。如果程式碼仍是唯一的事實來源，開發者會把大部分時間花在讀 AI 產生的程式碼，而且永遠追不上。

### 好消息：AI 也讀得懂規格

以前維護規格太貴，現在情況不同了。同一個 AI 既能照規格寫程式，也能拿規格回頭檢查程式。

所以規格驅動開發（Spec-Driven Development，SDD）的想法很簡單：**人不要再去追程式碼，改成把力氣放在規格上。人決定要什麼，工具檢查有沒有做到**。先把規格講清楚，審查才有依據，不用逐行猜 AI 的意圖。

## spec-kit 全貌：四個階段


![spec-kit 工作流程：4 個階段、8 個指令](/blog/spec-kit/spec-workflow.png)

spec-kit 是 GitHub 開源的工具包，用一組指令帶 AI 走完規格驅動開發。整個流程分成四個階段，每個階段只回答一個問題，而且不越界：spec 不寫技術、plan 不偷改需求、做完再拿程式碼對照規格。

converge 找到落差就回到 implement 補做；需求改了，就回頭改 spec，再往下走一次。clarify 和 analyze 是選用的，但很建議跑。



## 階段 0：先訂好專案的家規

`constitution`（憲法）聽起來很嚴肅，其實就是專案的家規。想像新人報到時拿到的員工手冊：規矩寫一次，主管不用每天提醒。

指令後面用白話寫你要的原則就好。我的瓦斯訂單系統訂了四條：

``` yml
/speckit.constitution 訂立專案原則：
1. 所有功能都必須有自動化測試
2. 採用三層架構：前端、後端 API、資料庫；部署一律用 docker-compose.yml 啟動
3. 安全底線：密碼一律用雜湊保存；API 存取必須通過身分驗證；所有對外 API 都必須有流量限制
4. 環境變數管理：.env 不進 git，必須提供 .env.example
```

跑完會得到 `.specify/memory/constitution.md`，四條規則被整理成正式條文，還加上版本號。寫家規時注意兩件事：

- **只寫長期的規則**：不管做什麼功能都要遵守的事。「要做登入」不是家規，那是下一步的事。
- **要寫成檢查得出來的句子**：「函式不得超過 50 行」檢查得出來，「程式碼要乾淨」檢查不出來。

家規不是寫完就放著。後面有三個指令會拿它來檢查：`plan` 在設計前後各檢查一次、`analyze` 只要違反就列為最嚴重、`converge` 檢查寫出來的程式有沒有違反。**規矩寫一次，AI 每一步都照著做**，你不用每次開新對話都重講一遍「記得寫測試」。

## 階段 1：說清楚要什麼（specify 與 clarify）

這一站是整套流程最重要的一站，因為 AI 亂猜的問題，就是在這裡解決的。

### specify：把口語需求變成 spec.md

每個新功能都從這個指令開始，它會替這個功能開一個新的資料夾。以供應商上架產品為例：

```
/speckit.specify 讓瓦斯訂單系統的供應商可以自己上架產品。
1. 商業目標：供應商不用透過管理員，可以自己上架和更新產品，消費者馬上看得到最新的產品和價格。
2. 規則：
   - 供應商可以上傳產品資訊、庫存數量和報價
   - 供應商可以修改或下架自己的產品
   - 庫存數量為 0 的產品，消費者頁面顯示「缺貨」
3. 成功條件：
   - 供應商上架後，消費者在現有的產品頁面看得到產品、價格和是否有貨
   - 消費者下單後，供應商看到的庫存數量已經扣掉
4. 不在這次範圍：營收報表、銷售統計（之後另開 spec）。
```

商業目標說明 Why，規則和成功條件說明 What。最後一點「不在這次範圍」很好用：直接告訴 AI 邊界在哪，它就不會自己多做。specify 的運作可以歸納成三個原則。

### 原則一：spec 不寫技術

Vue、React、Spring Boot 這些都留到下一個階段再決定。理由有四個：spec 是給 PM、客戶、主管也能看懂的；需求比技術穩定；避免 AI 太早下決定；同一份需求可以有不同做法。

判斷一句話該不該寫進 spec，只要問：**換掉技術，這句話還成立嗎？**

| 句子 | 換技術還成立？ | 屬於 |
| --- | --- | --- |
| 使用者登入後要進入首頁 | 成立 | spec（What） |
| 供應商可以修改或下架自己的產品 | 成立 | spec（What） |
| 身分驗證用 JWT 存登入狀態 | 不成立 | plan（How） |
| 前端用 Vue 加 Tailwind CSS | 不成立 | plan（How） |

### 原則二：大事問你，小事寫下來

specify 遇到沒講清楚的地方，不會全部自己猜，也不會全部問你：

- **大事 → 問你**：會大幅影響範圍或體驗、又沒有合理預設的決定，在功能需求那一行標成 `[NEEDS CLARIFICATION]`，最多 3 個，當場整理成選擇題問你。例如：什麼時候扣庫存？下單時、付款時，還是送達時？
- **小事 → 寫下來**：常識性的細節依業界慣例自己判斷，但寫進 spec 的 Assumptions 區塊，打開就看得到。例如：價格以新台幣計價、下架是隱藏而不是刪除。

問題不在 AI 會猜，而在它猜了卻不告訴你。這就是先寫規格跟純 vibe coding 的差別。

### 原則三：寫完先自我檢查

spec 寫完後，specify 會產生一份品質檢查清單（`checklists/requirements.md`），逐項檢查自己的 spec：有沒有混進技術細節、需求能不能測試、成功標準能不能量測、範圍有沒有邊界。沒過就自己改，最多重試 3 輪。

這就像替 spec 跑單元測試。例如 spec 裡寫了「庫存用 Redis 存」，就沒過「沒有實作細節」，它會改成「系統必須記錄每個產品的庫存數量」。

但這是 AI 檢查自己，只抓得到格式問題，抓不到需求本身錯了。**spec.md 出來之後，一定要人親自看過。**

### clarify：換 AI 反過來問你

specify 先擋住最大的風險，clarify 再系統性補洞。指令直接打 `/speckit.clarify` 就好，它會拿一份固定的分類清單掃過整份 spec，挑出影響最大的問題問你：

- 最多問 5 題
- 一次只問 1 題
- 每題附建議答案與理由，你回一個字母就好
- 答完直接寫回 spec.md

它不問按鈕顏色這種風格偏好，也不問技術選型。我實際跑的時候，它問我：「專案還沒有消費者產品頁面，這次要不要一起做一個最簡單的列表頁？」理由是我的成功條件寫了「消費者在產品頁看得到」，沒有這個頁面就沒辦法驗收。我原本以為頁面已經有了，這一題幫我抓到一個範圍漏洞。

## 回到開場的登入頁

如果當初先跑 specify 和 clarify，這兩個問題在寫程式之前就會被發現：

| 問題 | vibe coding | specify + clarify |
| --- | --- | --- |
| 登入後停在原地 | AI 自己決定，沒告訴我 | 標成 `[NEEDS CLARIFICATION]`：登入成功後導向哪個頁面？ |
| 密碼規則 | AI 自己訂了一套 | 寫在 Assumptions 讓我看到，或由 clarify 問：密碼規則為何？ |

問題從來不是 AI 笨，而是需求裡有空白，AI 沒問就自己填了。以前我花很多時間回頭找 AI 自己決定了什麼，現在這件事交給 converge。

不過也要說清楚：規格不可能一次就寫對。先問、再改、再檢查，來回幾輪是正常的。不要相信「一行指令就能完美打造系統」的說法。


## 階段 2：想好怎麼做（plan、tasks、analyze）

需求講清楚之後，技術到這裡才第一次登場。

### plan：決定技術，而且留下理由

plan 讀進三樣東西：spec.md、constitution.md，以及你寫在指令後面的技術方向：

```
/speckit.plan 前後端分離：後端用 Spring Boot 提供 REST API，前端用 Vue
```

**每個技術選擇都留下理由**。不確定的技術問題，plan 會先研究，再寫進 `research.md`，每項記三件事。以「兩個客人同時買最後一桶瓦斯，怎麼避免賣出兩桶」為例：

| 記錄 | 內容 |
| --- | --- |
| 選了什麼 | 扣庫存時用資料庫交易加鎖，一次只讓一個人扣 |
| 為什麼選它 | 目前只有一台伺服器、流量不大，這樣最簡單 |
| 考慮過什麼 | Redis 分散式鎖；要等伺服器變多才需要，現在用不到 |

最有價值的是最後一格。半年後有人打開這份文件，就知道當初不是不懂 Redis，是當時還不需要。

**家規會檢查兩次**。設計前先檢查技術方向，設計完再檢查一次，因為細節裡可能偷偷多了東西。例如家規是三層架構，設計卻多了 Redis。真的要違反，就要在 plan.md 的 Complexity Tracking 寫清楚三件事：違反了什麼、為什麼需要、為什麼不用更簡單的做法。說不出理由，就停下來。

plan 最後產出 `plan.md`、`research.md`、`data-model.md`、`contracts/`（API 規格）和 `quickstart.md`（驗證步驟）。它不寫程式、不拆任務，也不偷改需求。

### tasks：把計畫拆成待辦清單

tasks 讀進 plan.md 和 spec.md，依使用者故事把工作拆成一條條任務，存成 `tasks.md`：

```
- [ ] T012 [P] [US1] 建立 Product 模型，backend/src/model/Product.java
```

- `[ ]`：做完就打勾
- `T012`：任務編號，依執行順序
- `[P]`：可以平行，改的是不同檔案、互不依賴
- `[US1]`：對應 spec 裡的哪個使用者故事

任務按優先順序一個故事一個故事排。先做完 P1 的故事，就有一個可以展示的最小版本。測試任務是選用的：只有 spec 有要求測試，或你指定要用 TDD，才會產生。

### analyze：動手前的健康檢查

寫程式之前，analyze 把 spec、plan、tasks 三份文件拿來互相比對。官方分成六種問題，可以歸成三類：

| 類別 | 包含 | 例子 |
| --- | --- | --- |
| 寫得不清楚 | 模糊、規格不足 | 「頁面要快」，沒說要多快 |
| 文件對不上 | 重複、不一致、缺少任務 | spec 寫「缺貨不能下單」，tasks 卻沒有這條任務 |
| 違反家規 | 違反憲法 | 家規是三層架構，設計卻多了 Redis |

違反家規一律列為最嚴重。analyze 只出報告，不會自己動手改；要不要改、怎麼改，由人決定。

## 階段 3：做完對答案（implement 與 converge）

### implement：照清單把程式做出來

implement 讀進 tasks.md 和 plan.md，照清單一個階段一個階段做，做完一項就在 tasks.md 打勾。順序是：

1. **建置**：建資料夾、裝套件、寫設定檔
2. **測試**：先寫好驗收標準，例如「登入成功後要進到首頁」。這時功能還不存在，測試一定不會過
3. **核心**：寫功能本身，寫到測試通過為止
4. **整合**：接上外面的系統，例如資料庫、Google 登入、登入紀錄
5. **收尾**：補測試、調效能、更新文件

中間三步是每個使用者故事各走一輪，註冊走一輪、登入再走一輪，這樣做完一個就能先拿出來用。測試一步只在 tasks.md 有測試任務時才會做。一句話記：tasks 決定先測什麼，implement 照著先測再做。

### converge：拿程式碼對答案

converge 的做法像驗屋。它先從 spec、plan、tasks、家規整理出一份「應該做到的事」，再拿著清單，一條一條去程式碼裡找證據：

| 找到的結果 | 分類 | 驗屋的比喻 |
| --- | --- | --- |
| 完全找不到 | 沒做 | 合約寫三個插座，現場一個都沒有 |
| 有，但不完整 | 做一半 | 只裝了兩個 |
| 做法跟需求相反 | 做反了 | 合約寫木地板，結果鋪磁磚 |
| 程式裡有，需求沒寫 | 多做了 | 多了一面合約沒寫的牆 |

最關鍵的是：它不相信打勾。tasks.md 全部打勾，不代表真的做完，就像施工日誌全打勾，不代表房子照合約蓋。**打勾不算數，程式碼才算數**。

找到落差，它會在 tasks.md 最後面加上修正任務，不會自己改程式，也不會改 spec。接著再跑一次 implement，再跑一次 converge，直到全部對上。

要注意，判斷是 AI 讀程式碼做出來的，也可能看錯。它找出的落差是給人確認的線索，不是最終判決。



## 我的看法：優點與缺點

我的結論是：spec-kit 最大的價值不是這套工具本身，而是逼我們養成「先講清楚，再動手」的習慣。

**優點**

1. **規格變成資產**：規格是純文字，能反覆拿來產生、修改程式，不綁任何 AI 工具。今天用這個工具寫的規格，明天換工具也能繼續用。
2. **同一份規格，有機會產生不同取向的實作**：例如一個追求效能、一個追求低成本。不過這點官方還在實驗。
3. **從零開始的新專案最容易上手**：規格和程式從頭就是對齊的。舊專案也能用，但要先整理出現有的規矩，只替要改的部分寫規格，門檻比較高。

**缺點**

1. **維護成本可能上升**：官方說改需求只要重新產生計畫，幾分鐘就好。但在我自己的專案裡，功能越多，每個功能都有自己的 spec、plan、tasks，要同步的文件越多，維護成本反而上升。
2. **小改動走完整流程太重**：改個按鈕顏色，不需要寫規格。工具沒有強制，哪些改動值得走流程，要自己判斷。
3. **成效取決於模型，產出仍要人審查**：官方的前提是 AI 看得懂複雜的規格，這個前提成不成立，要看你用的模型。不管模型多強，每一步的產出都還是要人看過。

這也留一個問題給你：官方說 SDD 讓改需求變便宜，我的經驗是變貴了。你的專案會是哪一種？

## 下一步：用它繼續開發瓦斯訂單系統

讀書會後最常被問的是：「你有沒有用 SDD 做出來的成品？」所以接下來我會拿 spec-kit 繼續開發開場提到的瓦斯訂單系統，從供應商上架產品與自動扣庫存開始，把每一站的實際產出、踩到的坑和花的時間記錄下來，之後在這裡分享。

如果你想自己試試看，官方的安裝方式是：

``` yml
uv tool install specify-cli
specify init <專案名稱> --integration <你用的 AI 工具>
```

支援哪些 AI 工具、指令怎麼寫，以官方 README 為準。建議先從一個小功能開始，跑完 specify 和 clarify，就能感受到「讓 AI 先問清楚」的差別。
